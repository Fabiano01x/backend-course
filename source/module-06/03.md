### The Big Picture: Authentication vs. Authorization

Before we dive into code, it's crucial to distinguish between authentication (AuthN) and authorization (AuthZ).
*   **Authentication** is the process of verifying a user's identity. This is what we built with our login and refresh token system.
*   **Authorization** is the process of verifying if that authenticated user has permission to perform a specific action or access a resource.

### 1. Designing a Scalable RBAC Data Model

To implement RBAC, we first need to decide how to store roles in our database. A common, simple approach is to add a `role` column directly to the `User` table. However, this is inflexible as a user can only have one role.

For a production-grade system, a more robust and scalable design is a **many-to-many relationship** between users and roles. This allows a single user to have multiple roles (e.g., a user can be both an "editor" and a "moderator"). We will implement this superior model.

This requires three tables:
1.  `users`: Our existing user table.
2.  `roles`: A new table to store role definitions (e.g., 'admin', 'user').
3.  `user_roles`: An association table (or pivot table) to link users to their roles.

Based on the video, here is what the SQLAlchemy models would look like in our FastAPI project structure.

In a new file, `app/models/role.py`:
```python
from sqlalchemy import Column, Integer, String, Table, ForeignKey
from sqlalchemy.orm import relationship
from app.db.base_class import Base

# Association Table for User and Role
user_roles = Table(
    'user_roles',
    Base.metadata,
    Column('user_id', Integer, ForeignKey('user.id', ondelete='CASCADE'), primary_key=True),
    Column('role_id', Integer, ForeignKey('role.id', ondelete='CASCADE'), primary_key=True)
)

class Role(Base):
    __tablename__ = 'role'
    id = Column(Integer, primary_key=True)
    name = Column(String(50), unique=True, nullable=False, index=True)
    description = Column(String(255))
```

And you would update your existing `app/models/user.py`:
```python
# In your User model class...
# Add this relationship
roles = relationship("Role", secondary="user_roles", back_populates="users")

# And in your Role model class...
# Add the corresponding back-populates relationship
users = relationship("User", secondary="user_roles", back_populates="roles")
```

With this schema, you can now use Alembic to migrate your database to include these new tables and relationships.

### 2. Including Roles in the JWT Payload

For our RBAC system to be fast and stateless, the authorization checks should not require a database query on every single API request. The standard practice is to embed the user's roles directly into the JWT access token when they log in.

You'll need to modify your `/login` (and `/refresh`) endpoint. After successfully authenticating a user, fetch their roles from the database and add them as a custom claim to the JWT payload.

```python
# In your /login endpoint logic
# ... after verifying password ...

user_roles = [role.name for role in user.roles]

access_token_payload = {
    "sub": str(user.id),
    "roles": user_roles  # Add the roles list here
}
access_token = create_access_token(data=access_token_payload)

# Your final token payload might look like:
# { "sub": "1", "roles": ["admin", "editor"], "exp": 1678886400, ... }
```

### 3. Implementing the RBAC Dependency in FastAPI

Now for the core of our implementation. We will create a reusable **dependency** that can protect any endpoint. This dependency will:
1.  Depend on our existing authentication mechanism to get the current user's token payload.
2.  Extract the `roles` list from the payload.
3.  Check if the user's roles meet the requirements for the endpoint.
4.  If they do, allow the request to proceed. If not, raise a `403 Forbidden` HTTP exception.

Drawing inspiration from the video, here is a `RoleChecker` dependency adapted for our many-to-many model where a user can have multiple roles.

Create a new file, e.g., `app/dependencies/roles.py`:
```python
from fastapi import Depends, HTTPException, status
from typing import List
from app.auth.jwt_handler import get_current_user # Your dependency to get token payload

class RoleChecker:
    def __init__(self, allowed_roles: List[str]):
        self.allowed_roles = allowed_roles

    async def __call__(self, user: dict = Depends(get_current_user)):
        user_roles = user.get("roles", [])
        
        # Check if the user has any of the allowed roles
        if not any(role in self.allowed_roles for role in user_roles):
            # You can also check for all roles using:
            # if not all(role in user_roles for role in self.allowed_roles):
            
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail=f"You do not have the required permissions. Allowed roles: {', '.join(self.allowed_roles)}",
            )
```

### 4. Protecting API Endpoints

With our `RoleChecker` dependency ready, protecting endpoints becomes declarative and easy. First, you create instances of the checker for the roles you need.

```python
# In the same file or a central dependencies file
require_admin = RoleChecker(["admin"])
require_editor = RoleChecker(["editor"])
require_contributor = RoleChecker(["admin", "editor", "author"]) # User can be any of these
```

Now, you can apply these dependencies to your API routes.

```python
from fastapi import APIRouter, Depends
from .dependencies.roles import require_admin, require_contributor

router = APIRouter()

@router.get("/posts")
async def get_all_posts():
    # No dependency, so any user (even unauthenticated) can access
    return {"message": "Here are all the public posts."}

@router.post("/posts")
async def create_post(post_data: dict, user: dict = Depends(require_contributor)):
    # Only users with 'admin', 'editor', or 'author' role can create posts
    return {"message": f"User {user['sub']} created a post."}

@router.delete("/posts/{post_id}")
async def delete_post(post_id: int, user: dict = Depends(require_admin)):
    # Only users with the 'admin' role can delete posts
    return {"message": f"Admin {user['sub']} deleted post {post_id}."}
```
This approach is clean, readable, and highly maintainable—all qualities expected in a professional codebase.

You would change the check from `any()` to `all()`. The `all()` function ensures that every role in `self.allowed_roles` is present in the user's list of roles.

```python
# Inside the __call__ method of RoleChecker

async def __call__(self, user: dict = Depends(get_current_user)):
    user_roles = user.get("roles", [])
    
    # Check if the user has ALL of the allowed roles
    if not all(role in user_roles for role in self.allowed_roles):
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail=f"You do not have sufficient permissions. All of these roles are required: {', '.join(self.allowed_roles)}",
        )
```

### Conclusion

In this lesson, you've implemented a complete, production-ready RBAC system. You went beyond a simple implementation to build a scalable data model and used FastAPI's powerful dependency injection system to create clean, declarative, and reusable authorization logic.

**Key Takeaways:**
*   **Authorization vs. Authentication:** AuthN is about *who* you are; AuthZ is about *what* you can do.
*   **Scalable Data Model:** A many-to-many relationship between users and roles is the professional standard for flexibility.
*   **Stateless Authorization:** Embedding roles into the JWT payload avoids unnecessary database lookups on every request, making your API faster.
*   **Declarative Dependencies:** Using FastAPI's `Depends` for authorization keeps your business logic clean and separates concerns effectively.
