### 1. The "What" and "Why" of JWTs

Before we write any code, we need to understand what problem we're solving. In web applications, we need a way for a user to prove who they are (authentication) and then to verify they have permission to perform an action on every subsequent request (authorization).

Traditionally, this was done with server-side sessions, where the server stores information about a logged-in user and gives the client a session ID cookie. This is a **stateful** approach. JWTs enable a **stateless** approach.

#### Key Concepts from the Video:

*   **Structure:** A JWT is just a string, composed of three Base64-Url encoded parts separated by dots: `header.payload.signature`.
    *   **Header:** Metadata, like the token type (`JWT`) and the signing algorithm (`HS256`).
    *   **Payload:** Contains the claims—pieces of information about the user and the token itself. Standard claims include `sub` (subject, e.g., user ID), `exp` (expiration time), and `iat` (issued at). You can also add custom claims.
    *   **Signature:** This is the security part. It's created by hashing the header, the payload, and a secret key known *only* to the server. `HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), secret)`.
*   **Verification:** When the server receives a JWT, it re-calculates the signature using the received header, payload, and its own secret key. If the calculated signature matches the signature on the token, the token is considered valid and its payload can be trusted.
*   **Statelessness:** The server doesn't need to store any information about the token. All the necessary data for authorization (like user ID or roles) is contained within the token itself. This is highly scalable, especially in microservices architectures.

### 2. The Access and Refresh Token Pattern

If a JWT is self-contained and valid until it expires, what happens if it's stolen? The attacker can use it to impersonate the user until the token expires. A long expiry time (e.g., 30 days) is convenient for the user but creates a huge security risk. A short expiry time (e.g., 15 minutes) is more secure but would force the user to log in constantly.

This is the problem that the **access token / refresh token** pattern solves.

*   **Access Token:** A short-lived JWT (e.g., 15 minutes) that contains user information and is sent with every request to access protected resources.
*   **Refresh Token:** A long-lived token (e.g., 7 days) that has only one purpose: to get a new access token when the old one expires.

#### Summary of Implementation Steps

Let's distill the process shown in the video into a clear plan. For a "no-fluff" production setup, we can organize our code similarly to the structure suggested in the article `Bulletproof JWT Authentication in FastAPI`.

**1. Configuration (`app/core/config.py`)**

Your Pydantic `Settings` class should include JWT-specific configurations loaded from environment variables.

```python
# app/core/config.py
from pydantic import BaseSettings

class Settings(BaseSettings):
    # ... other settings
    JWT_SECRET_KEY: str
    JWT_ALGORITHM: str = "HS256"
    ACCESS_TOKEN_EXPIRE_MINUTES: int = 30
    REFRESH_TOKEN_EXPIRE_DAYS: int = 7

    class Config:
        env_file = ".env"

settings = Settings()
```

**2. Token Utilities (`app/auth/jwt_handler.py`)**

Create a dedicated module for token creation and decoding. This keeps your security logic isolated.

```python
# app/auth/jwt_handler.py
from datetime import datetime, timedelta
from typing import Dict, Any

import jwt
from app.core.config import settings

def create_access_token(data: dict, expires_delta: timedelta = None) -> str:
    to_encode = data.copy()
    if expires_delta:
        expire = datetime.utcnow() + expires_delta
    else:
        expire = datetime.utcnow() + timedelta(minutes=settings.ACCESS_TOKEN_EXPIRE_MINUTES)
    
    to_encode.update({"exp": expire, "iat": datetime.utcnow()})
    encoded_jwt = jwt.encode(to_encode, settings.JWT_SECRET_KEY, algorithm=settings.JWT_ALGORITHM)
    return encoded_jwt

def create_refresh_token(data: dict) -> str:
    expires_delta = timedelta(days=settings.REFRESH_TOKEN_EXPIRE_DAYS)
    return create_access_token(data, expires_delta)

def decode_token(token: str) -> Dict[str, Any]:
    try:
        payload = jwt.decode(token, settings.JWT_SECRET_KEY, algorithms=[settings.JWT_ALGORITHM])
        return payload
    except jwt.PyJWTError:
        # You can log the error here
        return None
```
*(Note: The logic here is adapted for a cleaner separation of access and refresh token creation compared to the video's single-function approach, which is a common refinement.)*

**3. Login Endpoint (`app/routers/auth.py`)**

Finally, use these utilities in your login route.

```python
# app/routers/auth.py
from fastapi import APIRouter, Depends, HTTPException, status
from fastapi.security import OAuth2PasswordRequestForm

# Assuming you have a user_service to get user and verify password
from app.services.user_service import UserService 
from app.auth.jwt_handler import create_access_token, create_refresh_token

router = APIRouter()

@router.post("/login")
async def login_for_access_token(form_data: OAuth2PasswordRequestForm = Depends()):
    # 1. Authenticate user (this logic depends on your user service)
    user = await UserService.authenticate_user(email=form_data.username, password=form_data.password)
    if not user:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Incorrect username or password",
            headers={"WWW-Authenticate": "Bearer"},
        )

    # 2. Create tokens
    # The 'sub' (subject) claim is standard for storing the user identifier
    access_token = create_access_token(data={"sub": str(user.id)})
    refresh_token = create_refresh_token(data={"sub": str(user.id)})

    # 3. Return tokens
    return {"access_token": access_token, "refresh_token": refresh_token, "token_type": "bearer"}
```

As a full-stack developer, it's crucial to know what happens next. Where do these tokens live on the client? Incorrect storage can completely undermine your backend security.

**The TL;DR on secure storage:**
*   **Access Token:** Store it in your application's memory (e.g., a variable in your React state management like Redux or Context API). **Do not** use `localStorage`, as it's vulnerable to XSS attacks.
*   **Refresh Token:** Store it in a secure, **`HttpOnly` cookie**. This makes the token inaccessible to JavaScript, providing strong protection against XSS. The browser will automatically send this cookie on requests to the token refresh endpoint.

### Conclusion

In this lesson, we laid the theoretical and practical groundwork for one of the most important aspects of API security. You now understand the stateless nature of JWTs and, more importantly, how to mitigate their risks using the access and refresh token pattern.

**Key Takeaways:**
*   **JWTs** are a stateless method for securely transmitting information for authorization. They are signed to ensure integrity but are not encrypted.
*   The **access/refresh token pattern** is the industry standard. It combines the security of short-lived tokens with the user experience of long-lived sessions.
*   The implementation in FastAPI involves creating **utility functions** to `encode` and `decode` tokens and an **endpoint** (`/login`) that validates credentials and issues both tokens.
*   **Secure client-side storage** is non-negotiable: access tokens in memory, refresh tokens in `HttpOnly` cookies.
