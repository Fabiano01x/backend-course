### 1. The Big Picture: OAuth 2.0 Authorization Code Flow

OAuth 2.0 is a protocol that allows an application (the "Client") to obtain limited access to a user's data on another service (the "Resource Server"), without exposing the user's password. The flow we'll use is called the **Authorization Code Grant**, which is the standard for web applications like ours.

It involves a few key steps:
1.  Our app redirects the user to Google's login page.
2.  The user logs into Google and "consents" to our app accessing their basic info.
3.  Google redirects the user back to our app with a temporary **authorization code**.
4.  Our backend server securely exchanges this code for an **access token**.
5.  Our server uses the access token to fetch the user's profile information (like email and name) from Google's API.
6.  We use that information to either find an existing user in our database or create a new one, and then log them in by issuing our own JWT.

### 2. Preparation: Registering Your App with Google

Before writing a single line of code, you must register your application with the OAuth provider. This process provides you with a unique `client_id` and a `client_secret` that identify your application.

The most critical part of this setup is defining the **Authorized Redirect URI**. This is a URL in your application where Google will send the user back after they have authenticated. It's a security measure to ensure Google doesn't send sensitive authorization codes to a malicious site. For local development, this will typically be something like `http://127.0.0.1:8000/api/auth/google/callback`.

### 3. Backend Implementation in FastAPI

Now let's translate the OAuth flow into FastAPI code. The process involves two main endpoints.

#### Endpoint 1: The Authorization Redirect (`/auth/google/login`)

This endpoint's sole job is to construct the correct URL and redirect the user to Google's authentication page. The URL must include several query parameters:

*   `client_id`: Your application's public identifier.
*   `redirect_uri`: The exact callback URL you registered in the Google Console.
*   `response_type`: Must be `code` to specify the Authorization Code flow.
*   `scope`: A space-separated list of permissions you're requesting (e.g., `openid email profile`).
*   `state`: A random, unguessable string that you generate and store (e.g., in a short-lived, secure cookie). Google will send this back to you in the callback. It acts as a crucial defense against Cross-Site Request Forgery (CSRF) attacks.

The logic is well-explained in Miguel Grinberg's article. Although the code is for Flask, the principles are identical.

Here is what this looks like in FastAPI. Notice how we set a `state` token in an `HttpOnly` cookie for CSRF protection.

```python
# In a file like app/api/endpoints/auth.py
from fastapi import APIRouter, Response, status
from fastapi.responses import RedirectResponse
import secrets

router = APIRouter()

@router.get("/auth/google/login")
async def google_login(response: Response):
    state = secrets.token_urlsafe(16)
    # Store state in a secure, httpOnly, short-lived cookie
    response.set_cookie(
        "oauth_state",
        state,
        httponly=True,
        max_age=600, # 10 minutes
        samesite="lax",
    )
    
    # These are from your config/environment variables
    GOOGLE_CLIENT_ID = "YOUR_GOOGLE_CLIENT_ID"
    REDIRECT_URI = "http://127.0.0.1:8000/api/auth/google/callback"
    
    # Construct the authorization URL
    scope = "openid email profile"
    authorization_url = (
        f"https://accounts.google.com/o/oauth2/v2/auth?"
        f"response_type=code&"
        f"client_id={GOOGLE_CLIENT_ID}&"
        f"redirect_uri={REDIRECT_URI}&"
        f"scope={scope}&"
        f"state={state}"
    )
    
    return RedirectResponse(url=authorization_url)
```

#### Endpoint 2: The Callback (`/auth/google/callback`)

This is where the core logic resides. After the user authenticates with Google, they are redirected here. This endpoint must perform a sequence of critical actions:

1.  **Validate the `state` token**: Compare the `state` query parameter from Google with the value stored in the `oauth_state` cookie. If they don't match, abort the request to prevent CSRF.
2.  **Exchange `code` for `access_token`**: Make a server-to-server `POST` request to Google's token endpoint. This request includes the `code`, your `client_id`, and your `client_secret`. **This must happen on the backend**, as the `client_secret` must never be exposed to the browser.
3.  **Fetch User Info**: Use the newly acquired `access_token` to call Google's user info API. This provides the user's email, name, etc.
4.  **Upsert User & Create Session**:
    *   Use the user's email to find them in your `users` table.
    *   If they exist, you've successfully authenticated them.
    *   If they don't exist, create a new user record. This is the "sign-up" part of social login.
    *   Finally, generate your application's own JWT (just like you do for password-based login) and set it in a cookie to establish a session.

Congratulations! You've just learned how to implement one of the most common and important features in modern web applications. By integrating OAuth2, you've not only improved the user experience but also offloaded the complexities of password management to a trusted provider like Google.

**Key Takeaways:**
*   **OAuth2 Authorization Code Flow:** You understand the multi-step dance between the user, your application, and the provider to securely grant access.
*   **Credentials and Configuration:** The `client_id` and `client_secret` are your application's identity, and the `redirect_uri` is a critical security boundary.
*   **Two-Endpoint Implementation:** A login flow requires an initial redirect endpoint (`/login`) and a `callback` endpoint to handle the response from the provider.
*   **Security is Paramount:** The `state` parameter is essential for preventing CSRF attacks, and the `client_secret` must always remain on the server.
*   **Integration with Your System:** After successful social login, you still create a local user record and issue your own JWT to manage the session within your application.
