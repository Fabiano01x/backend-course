### 1. The Vulnerability of Static Refresh Tokens

In the previous lesson's model, we issue a refresh token that might be valid for 7 days. If an attacker steals this token, they have a 7-day window to continuously generate new access tokens and maintain unauthorized access, even if the user changes their password. This is a significant security risk.

The solution is **Refresh Token Rotation**.

### 2. The Rotation and Reuse Detection Strategy

Refresh token rotation is a security pattern where every time a refresh token is used, it is immediately invalidated and replaced with a new one.

This strategy provides two major security benefits:

1.  **Shrinks the Attack Window:** If a refresh token is stolen, it can only be used once. As soon as the legitimate user or the attacker uses it, it becomes invalid, significantly limiting its usefulness.
2.  **Enables Breach Detection:** If the server receives a request with a refresh token that has *already been used*, it's a strong signal that the token was stolen. The system can then take immediate action, such as invalidating all active sessions for that user.

This flow is often called "rotation with reuse detection."

To implement this, we must shift from a purely stateless approach. We need a way to track the state of our refresh tokens on the server.

### 3. Storing Refresh Tokens in the Database

To know if a refresh token is valid, expired, or has already been used, we need to store it in our database. Since you're familiar with SQLAlchemy from the previous module, defining a model for this will be straightforward.

Let's design a `TokenBlocklist` model. We'll follow a structure similar to what you'd see in production systems.

```python
# In a new file, e.g., app/models/token.py
from sqlalchemy import Column, Integer, String, ForeignKey, DateTime, Boolean
from app.db.base_class import Base # Assuming you have a Base declarative_base

class TokenBlocklist(Base):
    id = Column(Integer, primary_key=True, index=True)
    jti = Column(String(36), nullable=False, index=True) # JWT ID
    token_type = Column(String(10), nullable=False) # "access" or "refresh"
    user_id = Column(Integer, ForeignKey("user.id"), nullable=False)
    expires_at = Column(DateTime, nullable=False)
    is_revoked = Column(Boolean, default=False, nullable=False)
```

**Key Fields Explained:**

*   `jti`: The "JWT ID" is a unique identifier for a token. We can add this claim when creating the JWT. It's the standard way to reference a specific token.
*   `user_id`: Links the token to a user.
*   `expires_at`: The token's expiration timestamp.
*   `is_revoked`: A boolean flag we'll use to invalidate a token. For rotation, we'll set this to `True` once a refresh token is used.

Storing the raw refresh token in the database is a security risk. If the database is compromised, an attacker would get a list of all active refresh tokens and could use them to impersonate users.

The recommended production practice is to store a **hash** of the refresh token (e.g., using SHA-256), not the token itself. When a refresh request comes in, you hash the provided token and look up the hash in the database. This way, a database breach doesn't expose the tokens directly. ### 4. Implementing the Refresh and Revocation Flow in FastAPI

Now, let's implement the complete server-side logic.

#### 4.1. Updating Token Creation and Login

First, we need to modify our JWT creation function to include the `jti` claim and then update our `/login` endpoint to save the refresh token to our new `TokenBlocklist` table. We'll use Python's built-in `uuid` module to generate a unique `jti`.

```python
# app/auth/jwt_handler.py
import uuid

def create_access_token(data: dict, expires_delta: timedelta = None) -> str:
    to_encode = data.copy()
    # ... (expiration logic remains the same)
    
    # Add jti claim
    to_encode.update({"exp": expire, "iat": datetime.utcnow(), "jti": str(uuid.uuid4())})
    encoded_jwt = jwt.encode(to_encode, settings.JWT_SECRET_KEY, algorithm=settings.JWT_ALGORITHM)
    return encoded_jwt

# In your /login endpoint, after creating the refresh_token:
# 1. Decode the refresh_token to get its 'jti' and 'exp'
decoded_refresh_token = decode_token(refresh_token)
# 2. Save to TokenBlocklist
db_token = TokenBlocklist(
    jti=decoded_refresh_token['jti'],
    token_type="refresh",
    user_id=user.id,
    expires_at=datetime.fromtimestamp(decoded_refresh_token['exp']),
    is_revoked=False
)
db.add(db_token)
await db.commit()
```

Now, let's build a production-grade `/refresh` endpoint that incorporates rotation.

```python
# app/routers/auth.py
@router.post("/refresh")
async def refresh_token(
    current_token: str = Depends(oauth2_scheme), # Assume oauth2_scheme gets token from header
    db: AsyncSession = Depends(get_db)
):
    try:
        payload = decode_token(current_token)
        token_jti = payload.get("jti")
        user_id = payload.get("sub")

        if token_jti is None or user_id is None:
            raise HTTPException(status_code=401, detail="Invalid token")

        # 1. Find the token in the DB
        # SELECT * FROM token_blocklist WHERE jti = token_jti AND user_id = user_id
        db_token_entry = await token_service.get_token_by_jti(db, jti=token_jti, user_id=user_id)

        # 2. Validate the token
        if not db_token_entry or db_token_entry.is_revoked:
            # THIS IS A SECURITY EVENT - REUSE DETECTION!
            # An attacker may be trying to use a stolen, old token.
            # Invalidate all of the user's refresh tokens.
            await token_service.revoke_all_user_tokens(db, user_id=user_id)
            raise HTTPException(status_code=401, detail="Token has been revoked. Please log in again.")
        
        if db_token_entry.expires_at < datetime.utcnow():
            raise HTTPException(status_code=401, detail="Token has expired")

        # 3. Invalidate (revoke) the old refresh token
        await token_service.revoke_token(db, jti=token_jti)
        
        # 4. Issue a new access token and a new refresh token
        new_access_token = create_access_token(data={"sub": user_id})
        new_refresh_token = create_refresh_token(data={"sub": user_id})
        
        # 5. Store the new refresh token
        decoded_new_refresh = decode_token(new_refresh_token)
        await token_service.add_token(
            db,
            jti=decoded_new_refresh['jti'],
            user_id=user_id,
            expires_at=datetime.fromtimestamp(decoded_new_refresh['exp'])
        )

        return {
            "access_token": new_access_token,
            "refresh_token": new_refresh_token,
            "token_type": "bearer"
        }

    except jwt.PyJWTError:
        raise HTTPException(status_code=401, detail="Invalid token")
```

#### 4.3. Implementing Logout (Revocation)

A proper logout mechanism on the backend is no longer just "delete the token on the client." It should invalidate the refresh token on the server so it cannot be used again.

The implementation is simple: create a `/logout` endpoint that finds the user's refresh token in the `TokenBlocklist` and sets `is_revoked` to `True`.

```python
# app/routers/auth.py
@router.post("/logout")
async def logout(
    current_token: str = Depends(oauth2_scheme), 
    db: AsyncSession = Depends(get_db)
):
    try:
        payload = decode_token(current_token)
        token_jti = payload.get("jti")

        # Revoke the refresh token
        await token_service.revoke_token(db, jti=token_jti)
        return {"message": "Successfully logged out"}
        
    except jwt.PyJWTError:
        raise HTTPException(status_code=401, detail="Invalid token")

```

### Conclusion

Today you've moved from a basic JWT implementation to a robust, secure authentication system that aligns with modern security best practices used in MNCs. By implementing refresh token rotation and reuse detection, you've drastically reduced the risk of token theft and built an early warning system for potential security breaches.

**Key Takeaways:**
*   **Static refresh tokens are a liability.** A single stolen token can grant long-term access.
*   **Refresh Token Rotation** solves this by ensuring each token is single-use.
*   **Server-side storage is essential** for rotation. We use a `TokenBlocklist` table to track the validity and state of refresh tokens.
*   **Reuse Detection is a powerful security pattern.** Identifying the use of a stale token allows you to proactively respond to a breach by invalidating all sessions for that user.
*   **Logout must be handled on the server** by revoking the refresh token, not just deleting it on the client.
