### 1. Why Async? The Engine and Session

FastAPI is built on an asynchronous framework (AsyncIO), which allows it to handle many concurrent requests without getting blocked by I/O operations like database queries or network calls. To take full advantage of this, our database interactions must also be asynchronous.

-   **The `Engine`**: This is the core of SQLAlchemy's connectivity. It's a factory for database connections and a connection pool. For our async FastAPI app, we will use `create_async_engine`. A traditional, synchronous `create_engine` would block FastAPI's event loop, defeating its main performance advantage.
-   **The `Session`**: This is your primary interface for talking to the database. You'll use a session object to add, modify, and query your model objects. Each session uses a connection from the engine to communicate with the database. In an async context, this will be an `AsyncSession`.

The fundamental pattern for a web application is **one session per request**. This ensures that each API request has its own isolated scope for database operations, preventing data conflicts between concurrent requests.

Your `database.py` should now look like this:

```python
# database.py

from sqlalchemy.ext.asyncio import create_async_engine, AsyncSession
from sqlalchemy.orm import sessionmaker, declarative_base

# 1. Database URL
# Format: "postgresql+asyncpg://user:password@host:port/dbname"
DATABASE_URL = "postgresql+asyncpg://user:password@localhost:5432/mydb"

# 2. Create the Async Engine
engine = create_async_engine(DATABASE_URL, echo=True)

# 3. Create a Session Factory
AsyncSessionLocal = sessionmaker(
    bind=engine,
    class_=AsyncSession,
    expire_on_commit=False, # Important for async usage
)

# 4. Create a Base class for your models
# This should be the same Base your models from the last lesson inherit from.
Base = declarative_base()
```

Let's break this down:
1.  **`DATABASE_URL`**: This connection string tells SQLAlchemy how to connect to your database.
    *   `postgresql`: The database dialect.
    *   `asyncpg`: The driver we are using.
    *   `user:password@localhost:5432/mydb`: Your database credentials, host, port, and database name. We will configure these with a Docker container shortly.
2.  **`engine`**: We create the async engine using our URL. `echo=True` is useful for development as it prints all the generated SQL queries to the console.
3.  **`AsyncSessionLocal`**: This is not a session itself, but a factory. When we call `AsyncSessionLocal()`, it will create a new `AsyncSession` instance for us, configured to use our engine.
4.  **`Base`**: This is the declarative base that your ORM models should inherit from. You can keep it here to be imported by your `models.py` file.

### 3. Managing Sessions via Dependency Injection

Now for the most important part: how do we provide a database session to our API endpoints and ensure it's properly closed afterward? FastAPI's **Dependency Injection** system is perfect for this.

We will create an asynchronous generator function that:
1.  Creates a new `AsyncSession`.
2.  `yield`s the session to the endpoint.
3.  Automatically closes the session when the request is complete (thanks to the `async with` block).

Add the following dependency function to your `database.py` file. This is the implementation of the "Dependency for Async Session" from the guide you just read.

```python
# database.py (continued)

# ... (engine, AsyncSessionLocal, Base definitions) ...

# Dependency to get a DB session
async def get_session() -> AsyncSession:
    async with AsyncSessionLocal() as session:
        yield session
```

This simple function is incredibly powerful. When used in an endpoint, FastAPI will:
1.  Call `get_session()`.
2.  Execute the code up to `yield session`.
3.  Inject the `session` object into your endpoint function.
4.  After your endpoint function returns a response, it will resume the generator, and the `async with` block will automatically handle closing the session.

This pattern ensures every request gets a clean session and that resources are never leaked.

### 5. Creating Database Tables on Application Startup

Our final step is to tell our application to create the database tables based on our SQLAlchemy models when it starts up. The modern way to handle startup/shutdown logic in FastAPI is with a `lifespan` event handler.

In your `main.py` file, you can define a lifespan context manager that runs your table creation logic.

```python
# main.py

from contextlib import asynccontextmanager
from fastapi import FastAPI, Depends
from sqlalchemy.ext.asyncio import AsyncSession

# Import your Base, engine from database.py and models
from .database import Base, engine, get_session
from . import models # Assuming your models are in models.py

@asynccontextmanager
async def lifespan(app: FastAPI):
    # On startup, create database tables
    async with engine.begin() as conn:
        # For production, you would use a migration tool like Alembic
        await conn.run_sync(Base.metadata.create_all)
    yield
    # On shutdown, you could add cleanup logic here

app = FastAPI(lifespan=lifespan)

@app.get("/status")
async def get_status(db: AsyncSession = Depends(get_session)):
    # This endpoint simply tests the database connection
    # by trying to get a session.
    is_connected = db.is_active
    return {"status": "ok", "db_connected": is_connected}
```
**Important Note:** The `Base.metadata.create_all` approach is great for development and testing. For production applications, you must use a database migration tool like **Alembic** to manage schema changes over time without losing data. We will cover Alembic in a later lesson.

### Conclusion

Congratulations! You have successfully configured your FastAPI application to connect to a PostgreSQL database using asynchronous SQLAlchemy. This is a robust, production-ready setup that you'll use as the foundation for all backend features.

**Key Takeaways:**

*   **Async is Key:** For FastAPI, use `create_async_engine`, `AsyncSession`, and an async driver like `asyncpg` to avoid blocking the event loop.
*   **Configuration is Centralized:** A `database.py` file is a good practice for holding your `DATABASE_URL`, `engine`, and `sessionmaker`.
*   **One Session Per Request:** The `Depends` pattern with an `async def get_session()` generator is the standard, reliable way to manage session lifecycles in FastAPI.
*   **Docker for Development:** Using Docker Compose to run your database simplifies your local development environment and mirrors production practices.
*   **Lifespan for Initialization:** FastAPI's `lifespan` event handler is the modern way to run logic (like creating tables) on application startup.
