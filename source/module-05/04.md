When a request hits a CRUD endpoint, several components work together:

1.  **FastAPI Path Operation:** A function decorated with `@app.post`, `@app.get`, etc. It defines the URL and HTTP method.
2.  **Pydantic Models:** These define the shape of the data for requests (e.g., the JSON body for creating a user) and responses. FastAPI uses them to automatically validate incoming data and serialize outgoing data.
3.  **Database Session (`AsyncSession`):** Injected into our endpoint via `Depends(get_session)`, this is our "handle" to the database for this specific request.
4.  **SQLAlchemy ORM:** We use the session to execute operations on our ORM model classes (e.g., `User`), which SQLAlchemy translates into SQL queries.

Let's assume you have a `main.py` and a `models.py` file. In `models.py`, you'd have your SQLAlchemy `User` model and the Pydantic schemas (`UserCreate`, `UserUpdate`, `UserResponse`). Now, let's add the endpoints to `main.py`.

#### Create (POST)

To create a new user, we receive a `UserCreate` Pydantic model, convert it into a SQLAlchemy `User` instance, add it to the session, and commit.

```python
# In main.py
from fastapi import FastAPI, Depends, HTTPException, status
from sqlalchemy.ext.asyncio import AsyncSession
from sqlalchemy.future import select

# Assuming these are in a 'models.py' file
from .models import User, UserCreate, UserResponse 
from .database import get_session, engine, Base

# ... (FastAPI app and lifespan setup from previous lesson) ...

@app.post("/users/", response_model=UserResponse, status_code=status.HTTP_201_CREATED)
async def create_user(user_in: UserCreate, db: AsyncSession = Depends(get_session)):
    # 1. Create a SQLAlchemy model instance from the Pydantic model
    user = User(**user_in.dict())
    
    # 2. Add the instance to the session
    db.add(user)
    
    # 3. Commit the transaction to the database
    await db.commit()
    
    # 4. Refresh the instance to get data from the DB (like the new ID)
    await db.refresh(user)
    
    return user
```
- `db.add(user)`: Stages the new `user` object to be inserted.
- `await db.commit()`: Persists all staged changes to the database in a single transaction.
- `await db.refresh(user)`: Updates the `user` object with the state from the database, which is useful for retrieving auto-generated values like the primary key.

#### Read (GET)

To read data, we use the `select()` function to build a query, execute it with the session, and process the results.

**Read a single user by ID:**
```python
@app.get("/users/{user_id}", response_model=UserResponse)
async def read_user(user_id: int, db: AsyncSession = Depends(get_session)):
    # 1. Create a select statement
    query = select(User).where(User.id == user_id)
    
    # 2. Execute the query
    result = await db.execute(query)
    
    # 3. Get the single scalar result (the User object)
    user = result.scalars().first()
    
    if user is None:
        raise HTTPException(status_code=404, detail="User not found")
        
    return user
```
- `result.scalars().first()`: A standard pattern. `scalars()` gives us the ORM objects themselves (not rows), and `first()` retrieves the first result or `None`.

**Read a list of all users:**
```python
@app.get("/users/", response_model=list[UserResponse])
async def read_users(skip: int = 0, limit: int = 100, db: AsyncSession = Depends(get_session)):
    query = select(User).offset(skip).limit(limit)
    result = await db.execute(query)
    users = result.scalars().all()
    return users
```
- `result.scalars().all()`: This fetches all results from the query as a list of `User` objects.

#### Update (PUT)

To update a user, we first fetch the existing record, then modify its attributes before committing the changes.

```python
@app.put("/users/{user_id}", response_model=UserResponse)
async def update_user(user_id: int, user_in: UserUpdate, db: AsyncSession = Depends(get_session)):
    # First, fetch the user (we can reuse our read_user logic or requery)
    result = await db.execute(select(User).where(User.id == user_id))
    user = result.scalars().first()
    
    if user is None:
        raise HTTPException(status_code=404, detail="User not found")
    
    # 1. Get the update data from the Pydantic model
    update_data = user_in.dict(exclude_unset=True)
    
    # 2. Update the model instance's attributes
    for key, value in update_data.items():
        setattr(user, key, value)
        
    # 3. Add the updated object to the session and commit
    db.add(user) # Stage the updated object
    await db.commit()
    await db.refresh(user)
    
    return user
```
- `user_in.dict(exclude_unset=True)`: This is a key pattern for partial updates (like PATCH). It creates a dictionary containing only the fields that were explicitly sent in the request body.

#### Delete (DELETE)

To delete a user, we fetch the record, tell the session to delete it, and commit.

```python
@app.delete("/users/{user_id}", status_code=status.HTTP_204_NO_CONTENT)
async def delete_user(user_id: int, db: AsyncSession = Depends(get_session)):
    result = await db.execute(select(User).where(User.id == user_id))
    user = result.scalars().first()
    
    if user is None:
        raise HTTPException(status_code=404, detail="User not found")
        
    # 1. Delete the object
    await db.delete(user)
    
    # 2. Commit the transaction
    await db.commit()
    
    return None # Return nothing for 204 No Content
```
- `await db.delete(user)`: Stages the object for deletion.
- A `204 No Content` response is standard REST practice for a successful deletion, indicating success by not returning a body.

### 2. Refactoring with the Repository Pattern

The direct approach works, but it mixes concerns. The API endpoint logic (handling HTTP requests/responses) is tightly coupled with the data access logic (SQLAlchemy session calls). This makes the code harder to test and maintain. If you wanted to switch from PostgreSQL to another database, you'd have to rewrite every single endpoint.

This is where the **Repository Pattern** comes in. It provides an abstraction layer between your business logic and your data storage.

The core idea is:
1.  **Define an Interface:** An abstract class that declares *what* data operations are needed (e.g., `get_by_id`, `add`, `delete`).
2.  **Create a Concrete Implementation:** A class that implements this interface using a specific technology, like SQLAlchemy.
3.  **Use the Interface in Your Logic:** Your API endpoints (or a "service" layer) will depend on the *interface*, not the concrete implementation.

Let's outline the structure for our `User` model, based on the article's example.

**Step 1: Create a `UserRepository` Interface and a Concrete Implementation**

Create a new file, `repositories.py`:

```python
# repositories.py
from abc import ABC, abstractmethod
from typing import List, Optional
from sqlalchemy.ext.asyncio import AsyncSession
from sqlalchemy.future import select

from .models import User, UserCreate, UserUpdate

class UserRepository(ABC):
    @abstractmethod
    async def get(self, user_id: int) -> Optional[User]:
        pass

    @abstractmethod
    async def get_all(self, skip: int, limit: int) -> List[User]:
        pass

    @abstractmethod
    async def create(self, user_in: UserCreate) -> User:
        pass
    
    # ... (interfaces for update and delete)

class SQLAlchemyUserRepository(UserRepository):
    def __init__(self, session: AsyncSession):
        self.db = session

    async def get(self, user_id: int) -> Optional[User]:
        result = await self.db.execute(select(User).where(User.id == user_id))
        return result.scalars().first()

    async def get_all(self, skip: int = 0, limit: int = 100) -> List[User]:
        result = await self.db.execute(select(User).offset(skip).limit(limit))
        return result.scalars().all()

    async def create(self, user_in: UserCreate) -> User:
        user = User(**user_in.dict())
        self.db.add(user)
        await self.db.commit()
        await self.db.refresh(user)
        return user
    
    # ... (implementations for update and delete)
```

**Step 2: Create a `UserService` (Optional but good practice)**

This "service layer" contains the business logic. It uses the repository.

```python
# services.py
class UserService:
    def __init__(self, repository: UserRepository):
        self.repo = repository

    async def create_user(self, user_in: UserCreate):
        # Here you could add more business logic, like checking for duplicates,
        # sending a welcome email, etc., before creating the user.
        return await self.repo.create(user_in)

    # ... (other service methods that call the repository)
```

**Step 3: Update FastAPI Endpoints**

Now, our endpoints become much cleaner. They only handle HTTP concerns and delegate all the work. We'll also need a dependency to provide the repository.

```python
# main.py

# New dependency to provide the repository
def get_user_repository(db: AsyncSession = Depends(get_session)) -> UserRepository:
    return SQLAlchemyUserRepository(db)

# ...

@app.post("/users/", response_model=UserResponse, status_code=status.HTTP_201_CREATED)
async def create_user_endpoint(
    user_in: UserCreate, 
    repo: UserRepository = Depends(get_user_repository)
):
    # The endpoint is now clean and delegates logic
    user = await repo.create(user_in)
    return user

@app.get("/users/{user_id}", response_model=UserResponse)
async def read_user_endpoint(
    user_id: int, 
    repo: UserRepository = Depends(get_user_repository)
):
    user = await repo.get(user_id)
    if user is None:
        raise HTTPException(status_code=404, detail="User not found")
    return user

# ... and so on for the other endpoints
```

The benefits are now clear:
- **Testability:** You can easily write unit tests for your service layer by providing a "mock" repository that doesn't touch the database.
- **Flexibility:** If you decide to switch to MongoDB, you only need to create a `MongoUserRepository` that implements the `UserRepository` interface. Your endpoints and services don't change at all.
- **Separation of Concerns:** Your code is organized, readable, and maintainable—hallmarks of a professional codebase.
