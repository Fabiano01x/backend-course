### 1. Why Good Schema Design is Non-Negotiable

Before we dive into the "how," let's establish the "why." In a rush to build features, it's tempting to create a single, large table to hold all related information. This approach quickly leads to significant problems.

A poorly designed database suffers from **data redundancy** and is prone to **anomalies**—bugs that corrupt your data when you try to insert, update, or delete records.

### 2. Normalization: The Process of Organizing Data

**Normalization** is the formal process of organizing the columns and tables of a relational database to minimize data redundancy and improve data integrity. It involves dividing larger tables into smaller, well-structured tables and defining relationships between them.

The process is defined by a series of **Normal Forms (NF)**. For most practical purposes in application development, achieving the **Third Normal Form (3NF)** provides the best balance of data integrity and practicality.

To summarize the core ideas:
*   **1NF (First Normal Form):** Ensures tables are "atomic." Each cell holds a single value, and there are no repeating groups. This is the most basic level.
*   **2NF (Second Normal Form):** Builds on 1NF and removes **partial dependencies**. All non-key attributes must depend on the *entire* primary key, not just part of it. This is only relevant for tables with composite primary keys.
*   **3NF (Third Normal Form):** Builds on 2NF and removes **transitive dependencies**. A non-key attribute cannot depend on another non-key attribute.

There is also **Boyce-Codd Normal Form (BCNF)**, which is a slightly stricter version of 3NF. While good to be aware of, a schema that is in 3NF is sufficient for the vast majority of production applications.

Let's distill the key takeaways that are standard practice in most tech companies:

*   **Start with the Domain:** Before writing any `CREATE TABLE` statements, identify the core **entities** (e.g., `Users`, `Products`, `Orders`) and the **relationships** between them (e.g., a `User` has many `Orders`; an `Order` has many `Products`).
*   **Use Surrogate Keys:** Almost always prefer an auto-incrementing integer (`BIGSERIAL`) or a UUID as your primary key over a "natural" key (like an email address). Surrogate keys are stable and meaningless, which prevents cascading updates if the business data changes.
*   **Enforce Foreign Key Constraints:** Always use `FOREIGN KEY` constraints in the database. They are your ultimate guarantee of referential integrity, preventing orphaned records. The minor performance overhead is a small price to pay for data consistency.
*   **Adopt Consistent Naming:**
    *   Use `snake_case` for all table and column names (e.g., `user_profiles`, `first_name`).
    *   Use **plural** table names (`users`, `orders`).
    *   Name foreign key columns `[referenced_table_singular]_id` (e.g., `user_id` in the `orders` table).
    *   Use `is_` or `has_` prefixes for booleans (`is_active`).
*   **Use Constraints Liberally:** Leverage `CHECK`, `UNIQUE`, and `NOT NULL` to enforce business rules at the database level. For example, `CHECK (price >= 0)`.

This schema is an excellent example of professional design. Let's highlight a few key features that demonstrate the principles in action:

*   **Many-to-Many Relationship:** Notice the `users`, `roles`, and `user_roles` tables. The `user_roles` table is a **join table** that resolves the many-to-many relationship between users and roles. It has a composite primary key `(user_id, role_id)`.
*   **Business Rule Enforcement:**
    *   The `enrollments` table has `CONSTRAINT uk_enrollment_student_course UNIQUE (student_id, course_id)`. This prevents a student from enrolling in the same course more than once—a critical business rule enforced by the database.
    *   The `courses` table has `CHECK (price >= 0)`, preventing negative prices.
*   **Soft Deletes:** Several tables (`users`, `courses`) have a `deleted_at TIMESTAMP NULL` column. Instead of permanently deleting records (which can orphan data or lose history), a common pattern is to "soft delete" by setting this timestamp. Queries for active records then include `WHERE deleted_at IS NULL`.
*   **Clear Naming:** The naming is perfectly consistent. `courses.instructor_id` clearly references the `users` table. `user_roles` is a plural name for a join table containing multiple user-role associations.

### 5. A Note on Denormalization

While our goal is to design a normalized schema (to 3NF), it's important to know that these rules are sometimes intentionally broken for performance reasons. This is called **denormalization**.

For example, in a reporting dashboard that needs to show the count of users per city, you might create a separate, denormalized table that stores `city_name` and `user_count` and is updated periodically. This avoids running an expensive `JOIN` and `COUNT(*)` query over a massive `users` table every time the dashboard loads.

The key takeaway is: **Normalize by default, denormalize only when you have a measured performance bottleneck.**
