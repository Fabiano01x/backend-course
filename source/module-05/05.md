Hello! Welcome back to our module on Database Modeling with SQLAlchemy.

In our last lesson, we built the core CRUD functionality for our application. However, we relied on `Base.metadata.create_all()` to set up our database tables. While convenient for getting started, this command is a major liability in a production environment. It can't handle changes to your models over time—if you add a new column, how do you update the live database table without losing all its data?

This is a critical challenge that every professional developer must solve. The solution is **database migrations**. This lesson will teach you how to **implement database migrations using Alembic to manage schema changes over time**.

Think of Alembic as Git for your database schema. It allows you to define, version, and apply incremental changes to your database structure in a safe, repeatable, and automated way. Mastering this is non-negotiable for building production-ready applications, aligning perfectly with your goal to learn "MNC perspective" skills.

Here's the summary:
*   **`alembic.ini`**: The main configuration file. It contains settings like the database connection URL.
*   **`alembic/`**: The main directory for migration logic.
    *   **`env.py`**: A crucial script that runs every time you use Alembic. It's responsible for connecting to your database and, most importantly, telling Alembic about your SQLAlchemy models.
    *   **`script.py.mako`**: A template file used to generate new migration scripts. You rarely need to touch this.
    *   **`versions/`**: This is where your migration files live. Each file represents a specific, versioned change to your database schema.

#### 1. Installation and Initialization

First, make sure you're in your project's virtual environment and install Alembic. You'll also need a database driver; since we're using async PostgreSQL, `asyncpg` is the right choice.

```bash
pip install alembic asyncpg
```

Now, from the root of your project directory, run the following command to create the Alembic environment:

```bash
alembic init alembic
```

You should now see the `alembic.ini` file and the `alembic/` directory in your project.

#### 2. Configuration

We'll follow a production-ready approach by using environment variables for the database URL, just as we did for our FastAPI application.

1.  **Import necessary modules and your models' `Base`:**

    ```python
    from logging.config import fileConfig

    from sqlalchemy.ext.asyncio import create_async_engine # Use async engine
    from sqlalchemy import pool

    # Import your models' Base
    from my_app.models import Base # Adjust the import path to your models file

    # ... other imports from the guide
    ```

2.  **Point `target_metadata` to your models:** This is how Alembic's `autogenerate` feature knows what your schema *should* look like.
    ```python
    # Find this line and change it
    # target_metadata = None
    target_metadata = Base.metadata
    ```

3.  **Configure the database connection for an async driver:** The `run_migrations_online` function needs to be adapted for `asyncpg`. The default is synchronous.

    ```python
    # Inside run_migrations_online()
    def run_migrations_online() -> None:
        """Run migrations in 'online' mode."""
        # This is the original connectable
        # connectable = engine_from_config(...)
        
        # We create our own async engine
        # Get the database URL from alembic.ini or environment
        db_url = config.get_main_option("sqlalchemy.url")
        connectable = create_async_engine(db_url, poolclass=pool.NullPool)

        # The rest of the function needs to run inside an async block
        async def run_async_migrations():
            async with connectable.connect() as connection:
                await connection.run_sync(do_run_migrations)

        import asyncio
        asyncio.run(run_async_migrations())

    def do_run_migrations(connection):
        context.configure(connection=connection, target_metadata=target_metadata)
        with context.begin_transaction():
            context.run_migrations()

    # ... (rest of the file)
    ```
    This setup ensures Alembic uses an asynchronous connection to talk to the database, matching our application's setup.

#### 3. Generating and Applying Migrations

With configuration complete, let's generate our first migration. Assuming your database is currently empty and you have your `User` model defined, Alembic will generate a script to create the `users` table.

**Step 1: Generate the migration script**

Run the `revision` command with the `--autogenerate` flag. The `-m` flag adds a descriptive message.

```bash
alembic revision --autogenerate -m "Create users table"
```

Alembic will inspect your database, compare it to the `target_metadata` you configured, and generate a new file inside `alembic/versions/`, something like `..._create_users_table.py`.

**Step 2: Review the script**
This is a critical best practice. **Always review auto-generated migration files.** Open the new file. You will see two functions:
*   `upgrade()`: Contains the logic to apply the change (e.g., `op.create_table(...)`).
*   `downgrade()`: Contains the logic to revert the change (e.g., `op.drop_table(...)`).

Given your SQL background, you can see that Alembic's `op` functions are Pythonic wrappers for generating SQL `CREATE TABLE`, `ALTER TABLE`, etc., statements.

**Step 3: Apply the migration**

Once you're satisfied with the script, apply it to the database using the `upgrade` command. `head` tells Alembic to upgrade to the latest revision.

```bash
alembic upgrade head
```

If you check your database now (e.g., with pgAdmin), you will see two things:
1.  The `users` table has been created with the correct columns.
2.  A new table named `alembic_version` exists. It contains one row with the revision ID of the migration you just applied. This is how Alembic tracks the database's current schema version.

#### 4. Managing Future Changes

Now, let's simulate evolving the application. Modify your `models.py` file and add a new column to the `User` model:

```python
# in your models.py, inside the User class
class User(Base):
    # ... existing columns
    is_active = Column(Boolean, default=True, nullable=False)
```

Now, just repeat the process:

1.  **Generate:** `alembic revision --autogenerate -m "Add is_active column to User"`
2.  **Review:** Open the new migration file. It should contain `op.add_column` in `upgrade()` and `op.drop_column` in `downgrade()`.
3.  **Apply:** `alembic upgrade head`

Your live database table is now updated with the new `is_active` column without losing any data. You've successfully managed a schema change!

### Conclusion

Congratulations! You've just learned one of the most essential skills for maintaining a real-world application. By replacing the brittle `create_all` method with a robust Alembic migration workflow, you can now evolve your database schema safely and systematically.

**Key Takeaways:**

*   **Migrations are Version Control:** Alembic provides a "Git-like" history for your database schema, making changes traceable and repeatable.
*   **The Core Workflow is `revision` and `upgrade`:** You use `alembic revision --autogenerate` to create migration scripts based on model changes and `alembic upgrade head` to apply them.
*   **Configuration is Key:** The most critical setup step is correctly configuring `alembic/env.py` to point to your database and your SQLAlchemy models' `Base.metadata`.
*   **Always Review Generated Scripts:** `autogenerate` is a powerful assistant, not an infallible authority. Always inspect the migration files it creates before applying them.
