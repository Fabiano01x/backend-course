### 1. The Power of Pydantic in FastAPI

When building an API, one of the most critical tasks is ensuring that the data sent by a client (like a React frontend) and the data sent back by your server is correct. Without a system for this, you'd be writing endless `if 'key' in data:` checks and manual type conversions, which is error-prone and tedious.

This is where Pydantic comes in. It's a data validation library that uses Python's type hints to validate and parse data. FastAPI is built on top of Pydantic, giving you its power for free.

When you use a Pydantic model to define a request body, FastAPI will automatically:

*   **Read** the incoming JSON data.
*   **Validate** that the data matches your model's structure and types.
*   **Convert** types where possible (e.g., a number sent as a string ` "42" ` can be converted to an integer `42`).
*   **Return a clear error** to the client if validation fails, pointing out exactly what was wrong.
*   **Generate** API documentation reflecting the expected data model.

Let's see how to put this into practice.

### 2. Defining Your First Data Model

A data model is simply a class that inherits from Pydantic's `BaseModel`. You define the fields of your data as attributes of the class, using standard Python type hints.

As you've just read, creating a model is straightforward. Let's imagine we're building an endpoint to create a new item in our application. We can define a model like this:

```python
from pydantic import BaseModel
from typing import Optional # Or use `| None` for Python 3.10+

class ItemCreate(BaseModel):
    name: str
    description: Optional[str] = None # An optional field with a default value of None
    price: float
    tax: Optional[float] = None
```

Here, `name` and `price` are required fields. If a client sends a request without them, FastAPI will automatically reject it with a `422 Unprocessable Entity` error. `description` and `tax` are optional.

### 3. Using Models for Request and Response

Now let's use this model in our FastAPI application.

#### For Request Validation (`POST`, `PUT`)

You simply use the model as a type hint for a parameter in your endpoint function. FastAPI handles the rest.

```python
from fastapi import FastAPI
from pydantic import BaseModel
from typing import Optional

app = FastAPI()

# --- Pydantic Models ---
class ItemCreate(BaseModel):
    name: str
    description: Optional[str] = None
    price: float
    tax: Optional[float] = None

# --- API Endpoint ---
@app.post("/items/")
async def create_item(item: ItemCreate):
    # 'item' is now a Pydantic object with validated data
    print(f"Creating item: {item.name}")
    # You can access attributes directly: item.price, item.description
    
    # We can convert the model to a dict to work with it
    item_dict = item.model_dump()
    
    # Simulate adding a calculated field
    if item.tax:
        price_with_tax = item.price + item.tax
        item_dict.update({"price_with_tax": price_with_tax})

    return item_dict
```

If you run this and send a `POST` request to `/items/` with invalid JSON (e.g., missing `name` or `price` as a string), FastAPI will automatically send back a helpful JSON error response.

#### For Response Validation (`response_model`)

It's also a best practice to define the shape of the data you're sending back to the client. This is done with the `response_model` argument in the path operation decorator.

This serves two purposes:
1.  **Filtering:** It ensures you only send back the fields defined in the response model, preventing accidental leakage of sensitive data (like user passwords or internal state).
2.  **Documentation:** It tells the API documentation (and developers using your API) exactly what to expect in the response.

Let's define a separate model for our response, which will include an `id` that the database would typically generate.

```python
# --- Pydantic Models ---
class ItemCreate(BaseModel):
    name: str
    description: Optional[str] = None
    price: float
    tax: Optional[float] = None

class ItemOut(BaseModel):
    id: int
    name: str
    description: Optional[str] = None
    price: float

# --- API Endpoint ---
@app.post("/items/", response_model=ItemOut)
async def create_item(item: ItemCreate):
    # In a real app, you would save `item` to a database
    # and get back an object with an ID.
    # Here, we'll simulate it.
    
    # The dictionary we return has extra data ('tax' and 'owner')
    # but `response_model=ItemOut` will filter it out.
    created_item_data = {
        "id": 123,
        "name": item.name,
        "description": item.description,
        "price": item.price,
        "tax": item.tax,  # This will be filtered out
        "owner": "admin"  # This will also be filtered out
    }
    
    return created_item_data
```

When you call this endpoint, the response will only contain `id`, `name`, `description`, and `price`, exactly matching the `ItemOut` model.

### 4. Advanced Validation with `Field` and Special Types

Basic type validation is great, but real-world scenarios require more specific rules. For example, a username shouldn't be empty, a password must meet complexity requirements, and an age must be within a reasonable range.

Pydantic's `Field` allows you to declare these constraints directly in your model. You can also use special, pre-validated types for common data formats like emails and URLs.

Let's apply these concepts to a `UserCreate` model:

```python
from pydantic import BaseModel, Field, EmailStr
from typing import Optional

class UserCreate(BaseModel):
    username: str = Field(
        ...,  # The ellipsis (...) marks the field as required
        min_length=3, 
        max_length=50, 
        pattern="^[a-z0-9_]+$"
    )
    email: EmailStr  # Pydantic will validate this is a valid email format
    full_name: Optional[str] = Field(None, max_length=100)
    age: Optional[int] = Field(None, ge=18, le=120) # ge = Greater or Equal, le = Less or Equal
```

Now, our `UserCreate` model is much more robust. It enforces business rules directly at the data layer, before your logic even runs.

### 5. Custom Validation Logic

What if your validation logic is too complex for `Field`? For example, you need to ensure that a password does not contain the username. Pydantic provides `@field_validator` (or `@validator` in Pydantic v1) for this.

This decorator allows you to define a method that receives the field's value and performs any validation you need. If the validation fails, you simply raise a `ValueError`.

Here's an example for password complexity:

```python
import re
from pydantic import BaseModel, Field, field_validator, EmailStr

class UserRegister(BaseModel):
    email: EmailStr
    password: str = Field(..., min_length=8)

    @field_validator("password")
    @classmethod
    def password_must_be_strong(cls, v: str) -> str:
        # Check for at least one lowercase, one uppercase, and one digit
        if not re.search(r"[a-z]", v) or \
           not re.search(r"[A-Z]", v) or \
           not re.search(r"[0-9]", v):
            raise ValueError("Password must contain at least one lowercase letter, one uppercase letter, and one digit.")
        return v
```

If a client tries to register with a password like `"password123"`, FastAPI will catch the `ValueError` and automatically return a `422` response with the message we provided. This integration is seamless and keeps your endpoint logic clean of validation clutter.

### Conclusion

In this lesson, you've learned how to wield one of FastAPI's most powerful features: its deep integration with Pydantic. By defining explicit data models, you create APIs that are robust, predictable, and largely self-documenting. This is not just a "nice-to-have"; it's a core requirement for building professional, enterprise-grade services.

**Key Takeaways:**

*   Pydantic models inherit from `BaseModel` and use Python type hints to define data schemas.
*   Use models as type hints in endpoint parameters to get automatic **request body validation**.
*   Use the `response_model` decorator argument to **filter and validate API responses**, preventing data leaks and ensuring a consistent contract.
*   Use `Field` to add advanced validation rules like length limits, numerical ranges, and regex patterns.
*   Use special Pydantic types like `EmailStr` for common data formats.
*   Implement complex custom logic with the `@field_validator` decorator by raising a `ValueError` on failure.
