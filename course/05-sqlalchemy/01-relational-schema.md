# Do dicionário ao esquema relacional

> **Origem e adaptação:** esta aula adapta *Database Schema Design for
> Full-Stack Applications*. O exemplo original de plataforma de cursos foi
> substituído pelo domínio cumulativo da Library API: usuários, livros e
> empréstimos.

O Módulo 4 terminou com dicionários Python. Eles foram úteis para aprender HTTP,
mas desaparecem ao reiniciar o processo e não conseguem proteger relações entre
dados concorrentes.

## O problema

!!! problem "O estado atual não possui memória nem integridade"
    Um livro e um usuário existem apenas dentro de um processo. Ainda não há
    histórico de empréstimos, garantia de ISBN único ou regra que impeça dois
    empréstimos ativos do mesmo exemplar.

Adicionar um dicionário `loans` resolveria apenas a aparência do problema. Nada
obrigaria os identificadores a apontar para registros existentes, e o booleano
`book.available` poderia divergir do histórico.

## Por que isso importa

Dados persistentes precisam continuar corretos mesmo quando outro endpoint,
processo ou ferramenta escreve no banco. Validação Pydantic protege a fronteira
HTTP; constraints protegem o estado compartilhado.

Três anomalias orientam o desenho:

- **inserção:** cadastrar empréstimo para usuário inexistente;
- **atualização:** marcar o livro disponível sem encerrar o empréstimo;
- **remoção:** apagar um livro e deixar seu histórico órfão.

!!! resource "Leitura — constraints no PostgreSQL"
    Consulte [Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html)
    na documentação oficial. Relacione `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`,
    `NOT NULL` e `CHECK` aos estados inválidos que cada regra impede.

## O conceito

Normalizar é separar fatos por entidade e armazenar cada fato essencial em um
único lugar. Para este domínio:

```text
users 1 ─────< loans >───── 1 books
```

Um usuário possui muitos empréstimos; um livro possui muitos empréstimos ao
longo do tempo. Cada empréstimo pertence a exatamente um usuário e um livro.

Aplicamos as formas normais de maneira prática:

- valores são atômicos, sem listas dentro de uma coluna;
- cada tabela tem uma chave estável `id`;
- atributos descrevem a chave da própria tabela;
- relações usam chaves estrangeiras, não cópias de nome, e-mail ou título.

!!! correction "Normalizar não é criar uma tabela para cada palavra"
    `author` continua como atributo textual de `books`. A aplicação ainda não
    gerencia autores como entidades com identidade e ciclo de vida próprios.
    Uma tabela `authors` agora seria abstração sem consumidor.

## Modelo mental

!!! mental-model "Tabela guarda fatos; constraint recusa contradições"
    `books` guarda o fato de que um exemplar existe. `loans` guarda quem o
    tomou e por qual intervalo. Disponibilidade é uma pergunta sobre esses
    fatos, não outro fato independente para manter sincronizado.

    ```text
    existe loan do livro com returned_at IS NULL?
              sim ──> indisponível
              não ──> disponível
    ```

## Exemplo mínimo

Este exemplo isola uma relação e não representa todo o esquema atual:

```sql
CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(254) NOT NULL UNIQUE
);

CREATE TABLE loans (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users (id)
);
```

A chave estrangeira impede que `loans.user_id` aponte para uma linha ausente.

## Aplicando ao projeto

O blueprint completo está em `schema.sql` no checkpoint. `users` preserva o
contrato atual e torna e-mail único:

```sql
CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(120) NOT NULL,
    email VARCHAR(254) NOT NULL,
    active BOOLEAN NOT NULL DEFAULT TRUE,
    CONSTRAINT uq_users_email UNIQUE (email),
    CONSTRAINT ck_users_name_not_blank CHECK (btrim(name) <> '')
);
```

`books` não armazena `available`. ISBN identifica o registro no catálogo e
recebe unicidade; título e autor não podem ser vazios.

`loans` é uma entidade, não apenas uma tabela de junção, porque possui datas:

```sql
CREATE TABLE loans (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL,
    book_id BIGINT NOT NULL,
    borrowed_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    due_at TIMESTAMPTZ NOT NULL,
    returned_at TIMESTAMPTZ,
    CONSTRAINT fk_loans_user
        FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE RESTRICT,
    CONSTRAINT fk_loans_book
        FOREIGN KEY (book_id) REFERENCES books (id) ON DELETE RESTRICT,
    CONSTRAINT ck_loans_due_after_borrowed CHECK (due_at > borrowed_at)
);
```

Uma constraint `CHECK` examina uma linha. A regra que compara empréstimos
diferentes usa um índice único parcial:

```sql
CREATE UNIQUE INDEX uq_loans_one_active_per_book
    ON loans (book_id)
    WHERE returned_at IS NULL;
```

Assim, vários empréstimos devolvidos podem compartilhar `book_id`, mas somente
um registro ativo é aceito. A documentação do PostgreSQL confirma que restrições
de unicidade sobre apenas parte das linhas são expressas por índice parcial.

!!! guidance "Fronteira desta aula"
    Ainda não instalamos SQLAlchemy nem conectamos PostgreSQL. Primeiro
    estabilizamos o significado das tabelas. A execução do DDL e sua tradução
    para modelos entram nas próximas aulas.

## Antes e depois

| Módulo 4 | Módulo 5 / Aula 1 |
|---|---|
| dicionários por processo | blueprint relacional persistente |
| relações sem garantia | chaves estrangeiras explícitas |
| ISBN pode repetir | ISBN único no banco |
| `available` armazenado | disponibilidade derivada do empréstimo ativo |
| nenhum histórico | `loans` preserva intervalos |
| regra apenas no endpoint | constraints recusam estados inválidos |
